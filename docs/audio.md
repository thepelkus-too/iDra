# Audio

## Architecture

```
mic / input device / file / stream URL / tab audio
        │
        ▼
AudioContext (HOST page) ──► AnalyserNode (512 samples) ──► Meyda loudness (24 Bark bands + total)
        │                                                          │
        └─► monitor gain ─► speakers                               ▼  postMessage {t:'audio', vol, specific} every animation frame
                                                       frame: HydraAudio.feed()  → a.vol / a.bins / a.fft / a0…aN / beat
```

Hydra's own `a` object (`hydra-synth/src/lib/audio.js`) opens the microphone in its constructor and cannot take a file or a stream, so
the runtime starts hydra-synth with `detectAudio: false` (the frame bundle stubs that module out) and installs `HydraAudio`
(`packages/core/src/hydra-audio.ts`) as `a`. It mirrors Hydra: `fft`, `bins`, `vol`, `setBins`, `setCutoff`, `setScale`,
`setSmooth`, `setMax`, `show`, `hide`, `onBeat`, `beat`, `settings` and the `a0…aN` helpers `setBins` creates. `feed()` is a
line-for-line port of `Audio.tick()`, and `detectBeat()` of `Audio.detectBeat()` (same adaptive threshold, hold and decay).

**Matching Hydra exactly** is tested two ways:

* `test/audio.test.ts` runs the **real** hydra-synth `Audio` class and `HydraAudio` on identical frames: identical `vol`, `bins`,
  `fft`, including after `setCutoff/Scale/Smooth/Bins`.
* `test/audio-sources.test.ts` decodes a fixed WAV (`test/fixtures/beats.wav`, generated by `scripts/lib/wav.mjs`: a quiet 220 Hz
  tone and a kick every 0.5 s, no third-party audio), runs Meyda on 512-sample hops, and feeds both implementations: identical
  values and the same beats on the same frames.

The frame message stays `{vol, specific}` (24 bands + total, ~0.5 kB), not pre-binned values, so a sketch's own
`a.setBins(8)` / `a.setCutoff(…)` behave exactly as in Hydra. Kept differences: no microphone in `a`, and `setBins(n)` with
`n > 24` gives zeros instead of throwing.

**`a.show()`** draws Hydra's bin meter **inside the preview frame** (bottom-right corner, as on hydra.ojack.xyz), because that
is where Hydra draws it and the sketch controls it: `a.show()` in code must show something without the editor knowing. The host
has its own meters (the audio panel, `audioBindings().subscribe`) for the chrome.

## Sources

`mountAudioPanel(el)` offers, in this order:

| source | how | notes |
|---|---|---|
| **Microphone** | `getUserMedia` with `echoCancellation`, `noiseSuppression`, `autoGainControl` **off** (they flatten the dynamics the visuals react to) | a refused permission says how to allow it (on iPad: Settings › Apps › Safari › Microphone, or the “aA” menu › Website Settings), it never throws at the sketch |
| **Input device…** | `enumerateDevices()`; *Find inputs* asks once so labels appear; the choice is remembered (`hydra-core:audioInput`) and matched by label if the id changed | a USB-C interface shows up here on iPadOS |
| **Audio file…** | the Files picker, played through `<audio>` + `MediaElementSource` (no full decode: a 10-minute track would be ~230 MB decoded) | transport: play/pause, seek, loop, file name and time; **keep on this device** stores it in IndexedDB (`hydra-ipad-audio`), max 60 MB per file and 250 MB in all, never in the sketch |
| **Stream URL…** | `<audio crossorigin="anonymous">` | see below. No stream URLs ship with the app. |
| **Tab / screen audio** | `getDisplayMedia` | only listed where the API exists (desktop Chrome/Edge; never iPadOS) |
| **Other apps…** | explanation only | a web page cannot record other apps' audio on an iPad: use the mic near the speaker, or a USB-C interface (line-in or a loopback cable) under *Input device* |

### Streams and CORS

Analysis of a stream needs the server to send `Access-Control-Allow-Origin`. `StreamSource` loads with `crossOrigin =
'anonymous'`; if that fails, a muted plain probe tells "plays but doesn't allow analysis" (error `no-cors`) from "unreachable".
The panel then says **"This stream plays but doesn't allow analysis"** and offers **Play without analysis** (the element plays
straight to the speakers; `a.fft` stays at 0). A stream that loads with CORS but only ever delivers zeros is reported as blocked
after ~1.5 s (`engine.analysis === 'blocked'`), with the same offer.

**HLS** (`.m3u8`): Safari (iPadOS and macOS) plays HLS natively, so an HLS URL with CORS on the playlist **and** the segments
analyses like any stream there. Other browsers have no native HLS and no HLS library is bundled (it would be ~100 kB+ for one
source type); the panel says so. Diagnostics → *HLS streams* reports `canPlayType('application/vnd.apple.mpegurl')`.

## Output and iOS behaviour

* Volume slider and mute for the monitor (what you hear). Live inputs start muted; with a live input **and** speakers on, the
  panel shows *"Mic and speakers are both on: this can feed back. Use headphones, or mute the speakers."*
* **Unlock:** iOS only starts audio from a gesture. The `AudioContext` is created and resumed by the tap on *Start*; the panel also
  unlocks on the first tap inside it. It does not listen page-wide, so tapping elsewhere never interrupts music you are playing in
  another app.
* **Interruptions** (calls, Siri, another app taking audio, backgrounding): the engine re-resumes on `statechange`,
  `visibilitychange`, `pageshow`, `pointerdown`, `touchend`. When that does not work, `engine.needsResume` is true and the panel shows
  **"Audio paused by the system · tap to resume"** (`resumeFromGesture()` also restarts file/stream playback).
* **Silent switch** (iPhones and some older iPads; current iPads have none, where this is a harmless no-op): iOS mutes Web Audio but
  not `<audio>`. `installSilentBypass()` sets `navigator.audioSession.type` (`'playback'`, or `'play-and-record'` with the mic;
  Safari 16.4+) and loops a generated 1-second silent WAV through an `<audio>` element from the same gesture, following
  [activetheory/ios-silent-bypass](https://github.com/activetheory/ios-silent-bypass) (MIT; our own code, nothing embedded).
* **Mic + speakers on iOS:** while an input is open, iOS may route output to the receiver or lower it. Not fixable from a page.

## Binding audio in editors

```ts
import { audioChip, audioSignalChip, audioBindings, parseAudioBinding } from '@hydra-ipad/core'
audioChip(1, 4, 0.5)                                                  // () => a.fft[1] * 4 + 0.5          (unchanged)
audioSignalChip({ kind: 'fft', bin: 0 }, { smooth: 0.8, scale: 2 })   // smoothed follower (a `js` value)
audioSignalChip({ kind: 'vol' }, { threshold: 4 })                    // () => (a.vol > 4 ? 1 : 0) * 1 + 0
const b = audioBindings()          // list() → fft0…fftN, vol, beat (meter only); chip(id, opts); identify(value)
b.subscribe('fft0', (v) => meter.value = v, { fps: 30 })   // live values for meters
```

`isSafeExpression` accepts exactly these chip forms, so they do not trigger the trust prompt. `parseAudioChip` still reads the plain
form and now also returns `smooth` / `threshold` when present.

## Latency and message overhead

Measured by `scripts/e2e-audio-plugins.mjs` in headless Chromium (software rendering, fake mic playing the test WAV; desktop numbers,
**not** iPad): about 57 messages per second of ~0.5 kB; host→frame delay (analysis frame emitted on the host → `a.vol` changed in the
frame at its next animation frame) median ~15 ms, p95 ~33 ms; plus the 512-sample analysis window (~11 ms at 44.1–48 kHz) and the
context's `baseLatency` (~10 ms): ≈ 37 ms audio→visual, under the ~100 ms target. Output latency of the display is not included.
The run writes `test-results/ipad/metrics.json`.

## On the iPad: what to check by hand

Nothing above proves iPadOS behaviour; CI only has Chromium with fake devices.

1. **Silent switch** (if the iPad has one): switch to silent, play a file: you still hear it.
2. **Mic + speakers:** start the mic with speakers on: the feedback hint shows; note whether iOS moves output to the receiver.
3. **USB-C audio interface:** connect it, *Input device… › Find inputs*: it is listed, analysis moves with its input, the choice is
   remembered after a reload.
4. **A streaming URL** with CORS (and one without): the first analyses, the second offers *Play without analysis* and plays.
   An HLS (`.m3u8`) URL with CORS analyses natively in Safari.
5. **Interruptions:** start audio, take a call or open another audio app, come back: either it resumes, or *tap to resume* appears
   and works.
6. **Web MIDI status:** Diagnostics › Web MIDI says `no`; a hydra-midi sketch shows the banner; the on-screen controller drives it
   (docs/midi.md).
7. **Camera in the sandboxed frame:** Diagnostics › *Probe camera in frame* (expected: denied, see docs/security.md).
